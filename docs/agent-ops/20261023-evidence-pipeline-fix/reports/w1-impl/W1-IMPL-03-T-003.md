**M-19 entry:**

```python
    # C07: next_id() must stay monotonic so two processes never mint the same
    # id; the same-millisecond increment is what makes ids unique within one
    # millisecond. Resetting the random component breaks uniqueness there.
    ("M-19", "src/research_engine/core/ids.py",
     '''            _last_random += 1
            if _last_random >= _RANDOM_LIMIT:''',
     '''            _last_random = 0
            if _last_random >= _RANDOM_LIMIT:''',
     "tests/unit/test_stage1_dead_legs.py::TestUlidIds"),
```

**Why this mutation breaks the invariant:** Within a single millisecond, the first call draws fresh entropy (`_last_random = os.urandom(...)` at `ids.py:82`); every subsequent call takes the else branch. With `_last_random = 0` instead of `_last_random += 1`, calls 2..N all encode random component `0` under the same millisecond stamp → byte-identical ids (collision) and no longer strictly increasing. This directly regresses the C07 guarantee ("ids unique and monotonic within a process", plan success criterion S3).

**Targeted test:** `tests/unit/test_stage1_dead_legs.py::TestUlidIds`. Under the mutation:
- `test_ten_thousand_ids_in_one_millisecond_are_unique_and_increasing` fails (collisions; not strictly increasing).
- `test_ids_stay_increasing_when_the_clock_moves_backwards` fails (older timestamp sorts before newer).
- `test_a_forked_child_does_not_continue_the_parent_counter` and `test_concurrent_minting_never_duplicates_an_id` also exercise the same increment path.

When reverted, `_last_random += 1` is restored and `TestUlidIds` passes (baseline already green).
